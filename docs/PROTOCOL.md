# Wuzhi ZK-502MT – Bluetooth protocol spec and feature list

Derived from the official Android app *Wuzhi Audio* v1.0.46 (`com.wuzhigoogle.audio`), by static analysis only.
Sections 1–11 were written before any hardware test; section 12 adds what testing on a real ZK-502MT showed. Test results and corrections are tracked in [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md). Every claim carries a confidence tag:

- **[V]** verified – reproduced by running the vendor's native code and matching its output
- **[D]** read directly from decompiled code (high confidence, but not run against hardware)
- **[I]** inferred / not seen in code – treat as a hypothesis and test on the device

This document states interoperability facts (UUIDs, byte layouts, opcodes). It contains no vendor code.
`reference/jl_auth.py` and `reference/frames_demo.py` are original implementations.

---

## 1. What the device speaks

The ZK-502MT's Bluetooth module is a **Jieli (JL) AC69xx** chip and the app talks Jieli's standard **RCSP** protocol over BLE **[D]**.
Wuzhi's own additions are small: one extra command family for the DSP/EQ screens (section 7). Almost everything else is stock Jieli.

The app is Jieli's reference demo app (`com.jieli.audio`) rebranded, plus ~600 Wuzhi UI classes. It is **not obfuscated** and has no packer.

## 2. Transport (BLE GATT) [D]

| Item | Value |
|---|---|
| Service | `0000AE00-0000-1000-8000-00805F9B34FB` |
| Write characteristic (host → device) | `0000AE01-…` |
| Notify characteristic (device → host) | `0000AE02-…` |
| MTU | app requests ATT MTU = payload + 3; payload bounds 20…514 |
| Writes | split into MTU-sized chunks, sent sequentially, each waited on (up to 8 s), retried up to 3 times |
| Receive | notifications are concatenated and re-split on frame boundaries (a frame may span several notifications) |

Classic Bluetooth is used only for audio (A2DP). The app also has an SPP path (`00001101`, custom `0000FE01`) that is a fallback for other products. [I] It is probably unused by this amp.

Open questions [I]:
- How the amp is recognised during scanning. The SDK has filters on a Jieli vendor ID (`0x05D6`) in advertising data; the exact rule used for this amp was not traced. Simplest approach: scan, list everything advertising service `AE00` or a name starting "ZK"/"JL", and let the user pick.
- Whether BLE bonding is required before the GATT connection works.
- Write type: the app does not override it, so Android's default applies. For Web Bluetooth use `writeValueWithResponse`.

## 3. Frame format [D]

```
FE DC BA | flags | opcode | paramLen (2 bytes, big-endian) | params … | EF
```

- `flags`: bit 7 = **1** for a command/notification from the initiator, **0** for a response. Bit 6 = **1** if the sender expects a response.
  All commands the app sends from the host have both bits set, so `flags = 0xC0`.
- `paramLen` counts everything between itself and `EF`.
- **params for a host → device command**: `sn` (1 byte sequence number, increment per command, wraps 255→0) followed by the opcode-specific payload.
- **params for a response (device → host)**: `status` (1 byte, 0 = OK), `sn` (echo), then payload.
- Multi-byte integers are big-endian.
- Receiving: find `FE DC BA`, read the length, expect `EF` at the end. Discard anything else.
- Replies are matched to commands by `(opcode, sn)`. App default timeout for a command: 2 s.

Worked examples (generated by `frames_demo.py`):

| Command | Frame |
|---|---|
| GetTargetInfo (all) | `fe dc ba c0 03 00 06 01 ff ff ff ff 00 ef` |
| GetSysInfo public, volume | `fe dc ba c0 07 00 06 02 ff 00 00 00 02 ef` |
| SetSysInfo volume = 20 | `fe dc ba c0 08 00 05 03 ff 02 01 14 ef` |
| Function: switch to AUX | `fe dc ba c0 0e 00 03 04 ff 03 ef` |
| DSP custom: query | `fe dc ba c0 ff 00 05 06 aa 01 1f 55 ef` |

## 4. Authentication handshake (mandatory) [V]

Before any RCSP frame, both sides authenticate on the same characteristics. These messages are **raw, not framed**
(no `FE DC BA`). The cipher is the Bluetooth legacy-pairing function **E1** (SAFER+), a published standard algorithm.

Constants (from `libjl_bluetooth.so`):

- 16-byte link key: `06 77 5F 87 91 8D D4 23 00 5D F1 D8 CF 0C 14 2B`
- 6-byte fixed "address" input: `11 22 33 33 22 11`
- The app can override the key with `setLinkKey` (16 bytes). In v1.0.46 nothing in the Wuzhi code sets it, so the default is in use. [D]

Algorithm: `response = 0x01 || E1(key, challenge[16], address[6])` (E1's full 16-byte output; do not truncate).
Reference implementation: `jl_auth.py`. It is checked against the vendor binary on these vectors:

| Challenge (16 B) | E1 output (16 B) |
|---|---|
| `00112233445566778899aabbccddeeff` | `26a69c072324c5e660c28ff912dcd857` |
| `00000000000000000000000000000000` | `9e43df377b3a46ce751634667e215de5` |
| `0102030405060708090a0b0c0d0e0f10` | `655d48686e418cf71f25fbc5cbeffa77` |

Message flow (17-byte challenge = `00` + 16 random bytes; the SDK uses `rand()`):

1. Host → device: `00 || R_host` (17 B).
2. Device → host: `01 || E1(key, R_host, addr)` (17 B). Host checks it matches its own computation. [D]
3. Host → device: `02 70 61 73 73` ("pass" with a `02` prefix) to say the device is accepted.
4. Device → host: `00 || R_dev` (17 B). Host replies `01 || E1(key, R_dev, addr)`.
5. Device → host: `02 70 61 73 73` = authenticated. [D]

Each step has a 2 s timeout, with up to 3 attempts overall. Only after step 5 are normal frames exchanged.
Whether steps 4–5 (device authenticating itself to the host) must be completed by the host for the amp to talk is [I]; implement the full exchange as the app does.

## 5. Connection sequence

1. Connect GATT, discover services, enable notifications on `AE02` (CCCD write), request MTU.
2. Run the auth handshake (section 4).
3. Send `GetTargetInfo` (opcode `0x03`, mask `FFFFFFFF`, platform `00`) – the app calls it with mask −1. [D]
4. Optional: `SettingsMtu` (opcode `0xD1`, payload = MTU as 2 bytes BE). [D]
5. Query state with `GetSysInfo` (opcode `0x07`) and show UI for whatever the device reports it supports.

The exact order the app uses after auth was not traced end to end; steps 3–5 are what it is known to do, but not necessarily in that order. [I]

### GetTargetInfo response [D]
Payload is a list of TLVs `[len][type][data(len-1)]`. Useful types:

| type | meaning | data |
|---|---|---|
| 0 | protocol version | `[hi nibble].[lo nibble]` |
| 1 | power-up info | `[battery][volume][max volume][flags]`; flags bit 0 = **volume sync supported** |
| 2 | EDR address | 6 bytes (+profile, status) |
| 3 | platform | **ASCII ID string on the ZK-502MT (hardware-tested)**; the SDK parses 3 like 13 on other firmware, ignore that |
| 13 | MTU | 2 B max receive MTU, 2 B max communication MTU |
| 4 | function info | which functions the device supports |
| 5 | firmware info | version code + version name |
| 10 | VID / PID | 2 B + 2 B |
| 11 | auth key | |
| 14 | allow-connect flag | |
| 16 | device name | UTF-8 |
| 17 | BLE-only flag | `[flag][6-byte BLE addr]` |
| 19 | supported functions | |
| 31 | custom version string | |

Type 4 and 19 use bitfield layouts that were not decoded; treat as [I].

## 6. Standard Jieli commands the amp UI uses [D]

Opcodes: `0x03` GetTargetInfo, `0x07` GetSysInfo, `0x08` SetSysInfo, `0x0E` Function, `0x01` Data, `0xFF` Custom (Wuzhi DSP, section 7),
`0xD0` NotifyAppInfo, `0xD1` SettingsMtu. All host commands in this list expect a response.
Other opcodes (file browse/transfer 0x16–0x24, OTA 0xE1–0xE8, TWS 0xC0–0xC4, speech, search-device 0x19, RTC expand 0x25) exist in the SDK and the app; they are not covered here.

### 6.1 Functions and attributes
`function` byte: `0` Bluetooth, `1` Music (USB/SD), `2` RTC/alarm, `3` Line-in/AUX, `4` FM, `5` Light, `6` FM transmit, `7` EQ, `0x16` low-power, `0xFF` **public** (global settings).

### 6.2 GetSysInfo (`0x07`)
Payload: `[function][mask: 4 bytes BE]`. Bit *n* of the mask requests attribute *n* of that function.
Response payload: `[function]` followed by TLVs `[len][type][data(len-1)]`.

Public (`0xFF`) attributes the app uses:

| attr | mask | meaning |
|---|---|---|
| 1 | `0x0002` | **volume** – `[vol]` |
| 4 | `0x0010` | **EQ** – `[mode][10 gain bytes]` |
| 6 | `0x0040` | current mode/function |
| 7 | `0x0080` | **light control** (11 bytes, 6.4) |
| 8 | `0x0100` | FM-TX frequency |
| 9 | `0x0200` | emitter mode |
| 0x0B | `0x0800` | **high / bass** – 2 × 32-bit BE |
| 0x0C | `0x1000` | EQ preset values |
| 0x0D | `0x2000` | current noise mode |
| 0x10 | `0x10000` | fixed-length data (reverb, dynamic limiter, …) |
| 0x11–0x13 | `0x20000–0x80000` | "sound card" mic EQ (not relevant to a pure amp) |

The all-public query used at startup is mask `0xFFF7` (`FF 00 00 FF F7`). [D]

### 6.3 SetSysInfo (`0x08`)
Payload: `[function]` + one or more TLVs `[len = 1+n][type][data(n)]`.

| What | function | attr | data |
|---|---|---|---|
| **Volume** | `0xFF` | 1 | `[vol 0…max]` (max comes from target info type 1) |
| **EQ preset / values** | `0xFF` | 4 | `[mode][g0…g9]` (11 B). Dynamic variant: `[mode|0x80][len][gains…]` |
| **High/bass** | `0xFF` | 0x0B | 8 B: `BE32(a) BE32(b)`; app strings call these Bass and "Height" (treble); which of a/b is which was not pinned down [I] |
| **Light** | `0xFF` | 7 | 11 B, see 6.4 |
| **Fixed-len data** | `0xFF` | 0x10 | `BE32(type) + data`. Types: 0 reverb, 1 dynamic limiter, 2 sound-card effect, 3 atmosphere, 4 mic arg. Data layouts of these were not decoded [I] |
| Music play mode | `1` | 2 | `[mode]` |
| FM-TX frequency | `0xFF` | 8 | `BE16(round(MHz × 10))` |
| Emitter mode | `0xFF` | 9 | `[mode]` |
| Noise mode | `0xFF` | 0x0D | mode bytes |

The EQ has 10 bands: 31, 63, 125, 250, 500, 1k, 2k, 4k, 8k, 16k Hz. Gain byte encoding for the standard EQ attribute (signed vs offset) was not confirmed [I]; the Wuzhi DSP EQ uses `dB + 12` (section 7).

### 6.4 Light control payload (11 bytes) [D]
```
[0]  switch (bit0..1) | lightMode << 2
[1]  R   [2] G   [3] B
[4]  twinkleMode   [5] twinkleFreq   [6] sceneMode
[7..8] hue (BE16)  [9] saturation   [10] luminance
```
App-side names: scenes (rainbow, heartbeat, candle, night light, stage, breath variants, music rhythm …), colour temperatures, flash modes (music-reactive, slow/quick), "shake phone to change colour".

### 6.5 Function command (`0x0E`)
Payload: `[function][cmd][extra…]`.

| Action | function | cmd | extra |
|---|---|---|---|
| **Switch source/mode** | `0xFF` | 0 BT, 1 Music, 2 RTC, 3 Line-in/AUX, 4 FM | |
| Play/pause (music) | 1 | 1 | |
| Previous / next (music) | 1 | 2 / 3 | |
| Play mode / EQ mode next | 1 | 4 / 5 | |
| Fast fwd / rewind | 1 | 7 / 6 | `BE16` step value (unit not confirmed) |
| AUX play/pause | 3 | 1 | |
| BT: play/pause, prev, next | 0 | 1 / 2 / 3 | (ID3 variants) |
| FM: play/pause | 4 | 1 | |
| FM: prev/next freq | 4 | 2 / 3 | |
| FM: prev/next channel | 4 | 4 / 5 | |
| FM: scan | 4 | 6 | `[dir]` |
| FM: select channel | 4 | 7 | `[idx]` |
| FM: delete channel | 4 | 8 | `[idx]` |
| FM: select frequency | 4 | 9 | `BE16(MHz × 10)` |

## 7. Wuzhi DSP / EQ commands (custom opcode `0xFF`) [D]

The only genuinely Wuzhi-specific protocol. Sent as RCSP opcode `0xFF`, `flags = 0xC0`, params = `sn` + a **DSP frame**:

```
AA | len | cmd | data … | 55          (len = number of bytes from cmd to the last data byte)
```

| cmd | Purpose | Layout | UI ranges seen |
|---|---|---|---|
| `0x0B` | **10-band EQ** | `AA 0C 0B 01 g0..g9 55` – gains are **dB + 12** (so −12…+12 dB → 0…24); the `01` after cmd is constant in the app | bands as 6.3 |
| `0x0C` | **L/R channel balance** | `AA 03 0C left right 55` | each 0…20 (UI default 2) |
| `0x0D` | **Gain** | `AA 03 0D stereoGain subGain 55` | each 0…14 (UI default 10) |
| `0x0E` | **Crossover filters** | `AA 05 0E stLow stHigh subLow subHigh 55` | indices; UI defaults: stereo 2/2, subwoofer 0/9; index→Hz mapping not found |
| `0x1F` | **Read info** | `AA 01 1F 55` | reply content is ignored by the app |

Behaviour notes:
- Commands are sent when a slider is released, not while dragging.
- The amp's reply to these is treated as "OK" regardless of content; the app does **not** parse values from it. The **DSP settings (gain, balance, filters) are only stored in the phone's preferences**, so the device cannot be read back. [D] A new app must persist them itself. [I] It's untested whether the `0x1F` reply carries state.
- The device may also push `0xFF` commands to the host. The app answers type-0/2 ones with a response. [D]
- UI warning when in DSP mode: "In this mode, only the main volume knob can be used."

## 8. Open items to settle on real hardware

1. The `0x1F` reply content (might carry current DSP state or the DSP mode flag).
2. Crossover filter index → frequency mapping, and sensible ranges.
3. Whether the amp needs BLE bonding, and which advertising fields identify it.
4. Meaning/order of the two 32-bit values in high/bass.
5. EQ gain byte encoding in the standard EQ attribute.
6. Whether unsolicited device notifications use opcode `0x07`/`0x08` pushes, and what triggers them (physical knob moves). Needed for live sync.
7. Which functions the ZK-502MT actually reports (target-info types 4 and 19): that decides which screens to show (FM, music, RTC, light).

To resolve these quickly: connect, run the handshake, send `GetTargetInfo` and the all-public `GetSysInfo`, log every frame, then turn the physical knobs and watch for pushes.

## 9. Features of the official app (to reimplement)

Based on screens and strings. Many are Jieli-generic and appear only if the amp reports support. [I] on which ones the ZK-502MT shows.

**Core (likely relevant)**
- Scan, connect, auto-reconnect, device list and history, rename device (name length limit enforced)
- Source switching: Bluetooth / AUX (line-in) / FM / Music (USB/SD) / RTC
- Main volume (with "volume sync" with the phone when the device supports it), plus Bass and Treble ("Height")
- Equalizer: presets (Normal, Pop, Rock, Jazz, Classical, Country, User) and a 10-band editor with a drawn curve; "advanced" page: reverberation (depth, strength), dynamic limiter
- DSP screen: stereo vs. subwoofer gain, crossover filters (two-handle sliders), L/R balance
- Light control: on/off, colour picker, colour temperature, scenes, flash modes, brightness, saved colours
- Firmware update (OTA) with progress and error reporting

**Secondary**
- FM radio: tune, scan, favourites list; FM transmitter frequency
- Music player for USB/SD: file browse, play modes, ID3 track info, seek
- Alarm clock / RTC with ringtone selection, time sync
- Mic EQ / sound-card effects (USB sound-card products; probably not this amp)
- Noise modes (denoise/transparent) and mic channel (headset products)
- Misc: beep volume, indicator brightness, find-my-device ring

**Not worth copying** – map (AMap SDK), crash reporting (Bugly), accounts/feedback form with phone number, net radio, "lullaby" content, in-app update downloader. These explain most of the app's permissions.

## 10. Feature ideas (noticed while reading the code, not investigated)

- **Persistent profiles for the DSP settings.** The device does not report them back, so the official app forgets them on a reinstall. Saving named profiles (e.g. "Movie", "Late night") and an export/import file is a real improvement.
- **Re-apply on connect.** Since DSP state is write-only, push the stored profile on every connection so the amp matches the app.
- **Per-source profiles** (different EQ/DSP for Bluetooth vs AUX).
- **Proper parametric-style curve view.** The app already draws a log-frequency EQ curve; a draggable version is natural.
- **Volume and source widgets / quick-settings tile**, and a bedtime fade-out timer (the amp has no timer, but the app can do it by lowering volume).
- **Web Bluetooth build** (Android Chrome): no install and no location permission; needs only the BLE service `AE00`. Writing the auth in JS is easy (the Python reference is about 60 lines).
- **Protocol logger / debug page**, which helps both development and closing the open items in section 8.

## 12. Addendum (after hardware testing + device-settings screen)

### 12.1 Corrections to earlier sections
- AE01 is **write-without-response only** (hardware-tested). Ignore the earlier note about write type.
- Target-info type 3 is an ASCII ID string on this amp, not the MTU (table in section 5 fixed).
- The function mask reports Music although the board has no USB/SD. The device's reported function list is unreliable; show screens based on the actual product, not the mask.
- DSP `0x1F` returns an empty reply (hardware-tested).
- EQ mode `0..6` = Normal, Rock, Pop, Classical, Jazz, Country, User (hardware-tested; the app's string order differs from the wire order).
- Opcode `0x09` is the SDK's `SYS_INFO_AUTO_UPDATE` [D]. The device pushes it with flags `0x80` (no reply expected). Payload is laid out like a GetSysInfo response: `[function]` + TLVs. Seen for EQ changes, AUX-cable insert (attr 2 bit 4) and source changes (hardware-tested).

### 12.2 Wuzhi device-settings commands (custom opcode `0xFF`, same `AA len cmd data 55` frame as section 7) [D]
Replies arrive as pushed `0xFF` custom commands in the same `AA … 55` format (the app answers them like any custom command).

| Setting | Write | Read → reply |
|---|---|---|
| **Bluetooth name** (the classic-BT name Android shows) | `AA (n+1) 05 name-bytes 55`; name ≤ 20 bytes, no terminator | none seen |
| **Pairing code on/off + code** | `AA 06 03 en d1 d2 d3 d4 55`: `en` 0/1, `d1..d4` = 4 ASCII digits (the app only sends exactly 4 characters; default "1111") | `AA 01 13 55` → `AA 06 13 en d1 d2 d3 d4 55` (9 bytes) |
| **Beep on/off + volume** | `AA 03 02 en vol 55`: `en` 0/1, `vol` 0…30 (UI default 15) | `AA 01 12 55` → `AA 03 12 en vol 55` |
| **Indicator LED brightness** | `AA 02 0A level 55`: level 0…8 (UI default 8). The slider is hidden behind a preference flag in this build | `AA 01 1A 55` → `AA 02 1A level 55` |
| **Authenticity / model query** | – | `AA 01 01 55` → ≥19 bytes: `AA len 01` + 3 ASCII model code (e.g. "005", the app maps it to "100") + 3 ASCII + 4 ASCII + 6 bytes (the app compares them, read as a number, with 180418 to decide genuine/not) |
| **TWS button** | `AA 01 0B 55` (no reply handling). Likely pairs two amps as a stereo pair [I] | – |
| **Sleep timer expiry** | `AA 01 04 55`, sent by the app **when its own lullaby timer ends**, right after it pauses phone playback. Almost certainly power-off/standby [I]; test with the volume low | – |

Notes:
- **"Shake and cut the song" is phone-only** (accelerometer + a "next track" command). No device command exists for it.
- The lullaby/white-noise screen plays local audio **on the phone** (8+ sounds with per-sound volume sliders) over normal A2DP, and its timer (15/30/45/60/90/120 min) is **phone-side**. Only the final `AA 01 04 55` involves the amp.
- Firmware version in the settings screen is the target-info type 5 version name ("V002.10" in the screenshot) [I].
- The pairing code and the DSP settings are cached in the phone's preferences; the device has read commands for code/beep/indicator, but not for the DSP values.

### 12.3 Other answers
- **Disconnect classic/A2DP:** SDK opcode `0x06` (`DisconnectClassicBluetooth`, no parameters, wants a response). The Wuzhi app never sends it, so its effect on this firmware is untested [I]. No "sleep"/"power off" command exists in the app besides `AA 01 04 55` above.
- **Target-info type 1** `[battery][volume][max volume][flags]`: only **bit 0 of flags is read (volume sync)**; bits 1–7 are not interpreted by the app.
- **Target-info types 7–0x0C:** 7 = bootloader version (string like "V1.2", or 2 bytes); 8 = OTA backup flags `[doubleBackup][needBootLoader][singleBackupOtaWay]`; 9 = `[mandatoryUpgrade][requestOta][expandMode]`; 10 = VID/PID (2+2 B BE); 11 = auth-key string; 12 = project-code string.
- **Sound card:** there is no separate function id. It lives in the public function `0xFF` as attrs `0x11` (EQ freq), `0x12` (EQ gain; set `[n][gains]`) and `0x13` (status; set `[id][BE16 value]`); GetSysInfo masks `0x60000` (EQ info) and `0x80000` (status). Not relevant to this amp.

### 12.4 More Wuzhi custom frames (main source screen) [D]
Found in `MultimediaFragment`. Same `AA len cmd data 55` frame inside opcode `0xFF`. Replies come back as pushed `0xFF` frames in the same format.

| cmd | Write | Read → reply |
|---|---|---|
| `0x08` | **Source select**: `AA 02 08 n 55`, n = 1 Bluetooth, 2 USB, 3 AUX, 4 sound card. The app sends it instead of the standard Function command. AUX/USB tiles are only enabled while the device reports that source online (target: online-device bit, type 4 = line-in) | none |
| `0x09` | **Product volume**: `AA 02 09 v 55` | `AA 01 19 55` → `AA 02 19 v 55` |
| `0x0F` | `AA 02 0F n 55`, appears to be the DSP control mode (0/1/2) [I]; the reply for 0x0F uses `[3]=8` | – |
| `0x1B` | – | **EQ readback**: `AA 01 1B 55` → `AA len 1B mode g0..g9 55` (≥15 bytes, gains are dB + 12) |
| `0x1F` | – | **DSP state**: `AA 01 1F 55` → `AA len 1F mode L R stGain subGain stLo stHi subLo subHi … 55` (≥12 bytes). The DSP screen ignores it, the main screen parses it; products without DSP return an empty reply |
| `0x01` | – | Model query (section 12.2). The 3-digit product code selects the UI: 1–3 / 4 / 5, 101 / 107 / 200 each show a different control set (plain, volume slider, "MAX GAIN" slider, DSP block) |
| `0x07` | – | second authenticity check (`AA 01 07 55`), used when a source is not online |
| `0x1C` / `0x33`, `0x22` | TWS swap `AA 01 1C 55` | TWS state query `AA 01 33 55` |

Note: custom frames must be sent in opcode `0xFF`. Sent in opcode `0x07` the amp reads the first payload byte as a GetSysInfo function id and the next bytes as a mask.
